# Veri Tabanı Şeması (PostgreSQL 16 + pgvector)

> Kaynak: `docs/plan/CareerAI_Proje_ve_GoLive_Plani.xlsx` (24.10.2026). Bu dosya ile Excel çelişirse bu dosya geçerlidir; değişiklikler PR ile buraya işlenir.

**KVKK kuralı:** CV dosyası ve ham CV metni hiçbir tabloda saklanmaz. Sadece SHA-256 hash, sayfa sayısı ve çıkarılan yetkinlikler (kullanıcı rızasıyla) tutulur.

**Genel kurallar:** Tüm tablolarda `created_at` / `updated_at` (timestamptz, varsayılan `now()`; `audit_logs` değiştirilemez kayıt olduğu için sadece `created_at`). Kullanıcıya bağlı tablolarda `ON DELETE CASCADE`. Şema değişiklikleri sadece Alembic migration ile yapılır (sahibi: Ataberk).

**ERD:** [`backend/app/db/erd.dbml`](../backend/app/db/erd.dbml) (dbdiagram.io → Import → DBML) · görsel: [`erd.svg`](../backend/app/db/erd.svg). Bu doküman ile ERD aynı PR'da güncellenir.

**Birincil anahtar (T-011):** Kullanıcıya ait ve id'si API'de görünen tablolar `uuid` (`gen_random_uuid()`): `users`, `refresh_tokens`, `user_tokens`, `consents`, `analyses` (tahmin edilebilir sıralı id yok). Katalog ve yüksek hacimli tablolar `int`/`bigint` identity (`GENERATED BY DEFAULT AS IDENTITY`; aşağıda "serial" yazan yerler böyle uygulanır). Sebep: `contracts/` içindeki `job_posting.id` ve `resource_id` integer; sözleşme değişmeden UUID'ye geçilemez.

**Soft delete (T-011):** `users` ve `analyses` tablolarında `deleted_at`. Silinen kayıt API'de görünmez; her gece çalışan iş 30 günü geçenleri kalıcı siler (CASCADE ile bağlı tüm kişisel veri gider, `audit_logs.user_id` NULL olur). Katalog tablolarında (`roles`, `skills`, `resources`, `job_sources`, `job_postings`) silme yerine `is_active`/`is_alive` ile pasifleştirme.

**Normalizasyon (3NF):** Türetilmiş değer saklanmaz. Bilinçli iki istisna: `analysis_skills.demand_ratio` (analiz anının anlık görüntüsü; sonradan değişmemesi gereken tarihsel değer) ve `role_skill_stats` (tablo değil materialized view, aşağıda).

## İlişkiler (özet)

```
users ─┬─< refresh_tokens
       ├─< user_tokens
       ├─< consents
       ├─< analyses ─┬─< analysis_skills >── skills
       │             ├─< analysis_unverified_skills
       │             ├─< analysis_recommendations >── resources >── skills
       │             └── feedback (1:1)
       └── target_role_id >── roles

job_sources ─< job_postings ─< job_posting_skills >── skills
job_sources ─< scrape_runs
roles × skills ─── role_skill_stats (materialized view, gece yenilenir)
audit_logs (denetim kaydı; user_id kullanıcı silinince NULL)
```

### `role_skill_stats` *(materialized view — T-011)*

Tablo olarak tutulursa `total_postings` sadece `role_id`'ye bağlı olur ve `demand_ratio` türetilmiş değer olur (3NF ihlali). Bu yüzden ham veriden hesaplanan bir **materialized view**'dur; gece toplama işinden sonra `REFRESH MATERIALIZED VIEW CONCURRENTLY role_skill_stats` ile yenilenir (T-045). Sütunlar aynı kaldığı için okuyan kod değişmez.

| Sütun | Tip | Açıklama |
|---|---|---|
| role_id | int | UNIQUE INDEX(role_id, skill_id) (CONCURRENTLY yenileme için şart) |
| skill_id | int |  |
| posting_count | int | Bu yetkinliği isteyen aktif ilan sayısı |
| total_postings | int | Pozisyondaki toplam aktif ilan |
| demand_ratio | numeric(5,4) | posting_count / total_postings → "%75" |
| computed_at | timestamptz | Yenileme zamanı |

```sql
CREATE MATERIALIZED VIEW role_skill_stats AS
WITH aktif AS (
  SELECT id, role_id FROM job_postings
  WHERE is_active AND role_id IS NOT NULL
    AND (posted_at IS NULL OR posted_at >= current_date - interval '6 months')
), toplam AS (
  SELECT role_id, count(*) AS total_postings FROM aktif GROUP BY role_id
)
SELECT a.role_id, jps.skill_id,
       count(DISTINCT a.id)::int AS posting_count,
       t.total_postings::int AS total_postings,
       round(count(DISTINCT a.id)::numeric / t.total_postings, 4) AS demand_ratio,
       now() AS computed_at
FROM aktif a
JOIN job_posting_skills jps ON jps.posting_id = a.id
JOIN toplam t ON t.role_id = a.role_id
GROUP BY a.role_id, jps.skill_id, t.total_postings;

CREATE UNIQUE INDEX ON role_skill_stats (role_id, skill_id);
```
